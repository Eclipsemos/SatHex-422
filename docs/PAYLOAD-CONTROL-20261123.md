# X26 感算载荷控制与重构验收 · 2026-11-23

适用版本为 gs422-payload-lab lab5、感算遥测大表 20261123 和《感算载荷在轨重构 OTA 协议》V1.0.1。验收对象是载荷应用软件。APP1/eMMC1 和 APP2/eMMC2 表示样例服务管理的两个软件槽。成功加载会启动候选容器并核对版本及就绪日志。更新 Ubuntu、boot 或原始分区不在这个映射内。

## 重构流程与线格式

控制口 UART6、快速上注口 UART8 均为 115200/8N1。文件首次传输前用 Z17 打开上注接收。查询版本 Z56 → 擦除非活动软件槽 Z55 → 开始 Z53 → UART8 上注若干 3A 包 → 结束 Z54 → 加载 Z04 → 再用 Z56 核对运行版本。数据口只收包，进度从控制口读。Z55 的目标应与 Z53 的目标一致。附录的示例分别写了 eMMC1 和 eMMC2。

| 项 | V1.0.1 实现 |
|---|---|
| 帧校验和 | OTA 类型 30、31、32、33、3A 的长度高、低字节与整个有效载荷逐字节相加，取低 16 位，大端。普通 K/D 遥控和原遥测沿用原帧。 |
| 应答 | 31H 有效载荷为类型、指令码、结果及五个零；32 14 查询回复 33 加一字节 TMG014。32 53 仍可读详细进度。 |
| 数据包 | 全帧 512 B，包序号 4 B，大端。数据域 499 B，首包依次放 4 B 文件长度、2 B 文件 CRC 和最多 493 B 正文。末包补零。文件 CRC 只覆盖正文。 |
| CRC | poly=1021H，init=0000H，RefIn/RefOut=false，xorout=0000H，结果高字节在前。实现使用这组明确参数，对应常用名称 CRC-16/XMODEM。V1.0.0 和 D0351 原有文件 CRC 保留各自定义。 |
| 断点和失败 | 重复包不增长计数，跳号可补发，Z54 缺包返回忙。坏帧丢弃。文件 CRC 错返回 11H 并上报 TMG013=05H、TMG014=24H。文件大小首次出现在 3A 首包，接收端只能在此时识别超限并上报 40H，无法在先前未携带大小的 Z53 预报 03H。 |
| 兼容范围 | lab5 为 V1.0.1 建立独立的暂存库。lab4 未结束的现代上注需重新发送。原普通遥控和 D0351 继续使用原通道格式。 |

### 附录示例校勘

| 输入 | 按明示参数复算 | 文档示例 |
|---|---|---|
| 空、单字节 00、单字节 FF | 0000、0000、1EF0 | 一致 |
| ASCII 123456789、128 个 FF | 31C3、EDA9 | 一致 |
| 499 个 FF 文件的 CRC | **80E3** | 7C6D |
| V2.0.0 版本应答帧的 SUM | **01D6** | 01E8 |
| 3A 数据域全 FF 的第 0、1 包 SUM | F240、F241 | 一致。该组数据可测帧校验，首包全 FF 会把文件长度声明成 FFFFFFFFH。 |

实际传输 499 个 FF 时，首包数据域以 `00 00 01 F3 80 E3` 起始，随后是 493 个 FF。第二包从 6 个 FF 开始，余下 493 B 补零。V1.2.3 版本示例应答 SUM 为 01DA。两端联调应使用相同的参数与测试字节。

## TMG014 和 TMG004

Z53 就绪后进入 20H。收齐全包时仍保持 20H。Z54 确认齐包后依次发布 21H、22H，最终 CRC 通过为 23H、失败为 24H。21H 是状态转移，协议没有规定最短驻留时间。正常运行不为轮询延长状态。加载开始为 30H，健康检查成功为 31H，服务重启后回到 00H。擦除期间为 10H，成功为 11H。已知业务失败为 40H，未预期的执行异常为 FFH。

X26 实物控制口测试中，测试夹具用伪终端送齐 499 B 文件，并只在夹具内延长 21H 的观察窗口。PC 的 COM3 同时验证了 32/14 短查询和 TYPE11 普通遥测均可回读 20H、21H、23H。夹具后端抛出受控异常后，两种查询均回读 FFH；下一次 Z53 后均为 20H。短查询的 21H 应答为 `EB 90 00 02 33 21 00 56 09 D7`，FFH 应答为 `EB 90 00 02 33 FF 01 34 09 D7`。实际 UART8 导线仍待接入。

TMG004 只返回最近收到的有效 UTC 广播，采用本项目约定的 `CC 01 UTC[4]`，大端 Unix 秒，服务重启至首次有效广播前为 0。星务正式接入后需确认广播子码。

## 三条遥控

| 指令 | 设计与实测 | 待接入 |
|---|---|---|
| K1104 / 83H | ID 对应本地登记的 CPU/NPU 镜像。数值较大的优先级先出队，同级 FIFO，非抢占。允许 2 个并发任务和 8 个等待任务。独占任务等待运行任务退出。重复 ID 拒绝。X26 在真实 Docker 中并行启动两个 CPU 样例，按 ID 分别停止。软件测试覆盖排队、独占、满队列、取消和后摩不可用。默认只注册 CPU 样例 ID 1。 | 后摩卡、驱动、设备节点、经验证的 NPU 镜像和业务算法数据。 |
| K1115 / 32H | 开启时固定模式与介质，同参数返回已有文件号。每帧提交数据，驱动停止成功才将记录标记完整。SSD 检查挂载点和 UUID，预留 16 MiB，持久化文件标识和索引。板上模拟星敏在 tmpfs 中分别记录三种模式；SSD 的身份检查、真实 SQLite 写入、空间不足、停止失败与重建索引由受控测试覆盖。 | 实际星敏的输入和模式控制驱动；实际 SSD 及其 UUID、挂载点。需做掉线、拔盘及掉电验证。 |
| D0351 / TYPE25 04H | 旧协议最多 256 包、128 KiB，沿用旧 CRC。CRC 通过后保留候选。显式 TYPE30/04 索引 00 按本地 SHA256 目录授权，检查镜像 ID，加载非活动应用槽并核对就绪信号。X26 用完整的小型 ARM64 Docker 包做乱序上注，查询升级前后的版本，重复激活，分别测试未登记包拒绝和健康检查失败后的旧软件恢复。 | 地面或星务实装发送端可再对测。该旧格式经遥控口传输。 |

可复现用例见 `tests/test_ota_v101.py`、`tests/test_revision_nov23.py`、`tests/live_payload_service.py`、`tests/live_v101_deployment.py`。运行物理控制夹具 `tests/live_v101_control.py` 需先释放 UART6，测试后恢复常驻服务。 配对的 PC 脚本为 `tools/verify-ota-v101-control.ps1`；加 `-Installed` 只查询常驻服务。
