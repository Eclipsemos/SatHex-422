# X26 载荷软件上注更新设计

2026-11-20范围更正：用户明确上注用于更新软件，通常不升级Ubuntu系统。此前的双Ubuntu、重新分区和U-Boot回退提案撤回，不实施；此前只改了设计文件，主板未被重新分区或改写启动链。

## 更新范围

UART8的RS422_RX2接收载荷程序、配套库、配置模板和资源包；UART6承载控制、应答和遥测。算法实现继续留空，未来有软件包再注册。Ubuntu、内核、设备树、系统模块、U-Boot及GPT不属于本次上注更新范围；不调用apt或系统刷写工具。

## 文件存储与协议映射

使用现有eMMC文件系统内的普通目录，主备是软件版本目录，不是物理分区：

| 路径 | 用途 |
|---|---|
| /var/lib/sathex/upload/ | 接收暂存、断点位图与事务记录 |
| /var/lib/sathex/software/slots/A/ | 软件A版本 |
| /var/lib/sathex/software/slots/B/ | 软件B版本 |
| /var/lib/sathex/software/current | 指向当前软件版本的链接 |
| /var/lib/sathex/software/packages/ | 已验证安装包与历史索引 |
| /var/lib/sathex/software/factory/ | 地面预置的已知可用软件包 |
| /var/lib/sathex/software/state/ | 激活事务和健康确认 |
| /var/lib/sathex/config/、data/、logs/ | 独立持久配置、业务数据及日志 |

建议APP1=03H/eMMC1=01H映射软件A槽；APP2=04H/eMMC2=02H映射软件B槽。eMMC1/2是协议逻辑区域，不是mmcblk0p1/p2。boot1/boot2本版保留并拒绝执行，不自行解释成系统启动分区或某个业务程序。SPI-NOR/SSD目前无可用映射，返回目标无效；交叉APP/区域组合拒绝。

初始预算建议：单包最多256MiB，单槽解包最多1GiB，两槽合计2GiB，历史包池1GiB，接收暂存预留1GiB，状态及日志上限256MiB，操作后系统仍至少剩余4GiB。实施时按statvfs、包解压大小和数据库/导出临时空间峰值核算，超限拒绝；不新增固定大小分区。大型算法模型当前不在范围内，以后单独确定配额及传输时间。

## 更新流程

1. 53H验证非活动槽、可用容量和包类型，建立或恢复接收会话。
2. UART8收包，使用已确认的CRC-16/CCITT-FALSE，持久化后再增加r010，支持查询缺包和重传。
3. 54H完成文件校验及包清单检查。此时只有“包已验证”，尚未改变运行程序。
4. 04H选择完整已验证包，解压到非活动槽的临时目录，核对每文件hash、架构、依赖与配置兼容性后提交候选目录。
5. 持久化PREPARED，停止目标业务服务，原子替换current，记录TRIAL，启动候选业务。
6. 最多60秒验证实际版本、进程存活、业务自检和必要资源；成功记录CONFIRMED，失败切回旧槽并重新启动旧业务，记录ROLLED_BACK。

默认只重启目标业务进程，不重启主板。K1109仍是独立的整板重启命令。固定更新管理器和遥测遥控服务不包含在可替换的业务包内，避免业务升级失去控制链路。以后若需更新管理器自身，需另定升级机制。

首次部署先把已有可运行业务登记为A槽基线，B为空；没有实际业务程序时不能创建假的成功版本。算法当前为空，暂不注册算法服务。允许以独立测试程序验证停启与回退，但必须标为测试替身。

包清单至少包含软件名、release、平台aarch64/X26、文件路径/hash、压缩与展开大小、依赖和配置schema。服务名和健康检查入口由本机白名单配置，不执行包内任意安装脚本。解包拒绝绝对路径、..、软链接逃逸和设备文件。依赖不满足就拒绝，不通过更换系统或自动安装依赖来掩盖不兼容。建议包签名验证，具体签名格式和密钥配置在实现时明确。

## 版本回退和断电恢复

slots、候选目录和current必须位于同一文件系统。日志与链接不能跨对象一次原子提交，因此采用PREPARED/TRIAL/CONFIRMED事务及明确fsync顺序；启动时核对事务和current，未确认候选回退旧版本，已确认事务保留新版本。不无限自动重试失败包。

配置、数据和日志位于槽外，不随升级删除。配置迁移先备份，并要求旧版本可读或可恢复；首版禁止不可逆数据库迁移。断电或回退后未完成任务标记中断，不盲目重放有副作用的动作。

此方案能处理业务启动失败、健康检查超时及软件激活阶段中断，不能处理Ubuntu无法启动或eMMC物理损坏，不宣称提供系统级回退。

## 55H与04H的具体语义

55H在本软件配置中仅操作受管目录，不执行裸Flash擦除。scope=00清理指定非活动槽的发布文件和候选资料；scope=01只清理该槽候选安装包与未激活的暂存资料。活动版本、唯一回退版本、factory包、业务数据和更新管理器不允许删除。若目标槽是唯一旧版本，先保存并验证可恢复副本，才允许清理。上述scope解释是新增软件配置约定，需要同步发送端。

04H安装和健康检查可能超过原文3秒控制超时。设计采用“持久化受理后00应答，随后查r014及56H确认最终结果”：r014=30加载中，健康确认成功才置31，失败置40并保留旧版本。00仅表示受理，不是已完成；这与原文立即“加载成功”应答不同，需在软件升级配置版本中明确，不能暗改发送端含义。未实现该扩展时，应明确拒绝执行，不能执行一半后让发送端自动重发。

56H报告实际激活的软件release，不用Ubuntu版本或上传文件名代替。没有注册业务软件时明确未配置。试运行状态必须通过状态查询区分；旧版本仍是最后已确认版本。历史包索引00/01–80/F0–FF按持久目录解析，不因文件排序而漂移；只注册实际存在且验证通过的恢复包。

本次仅修正设计与清单，不安装或激活任何软件。已有接收/暂存/CRC实现可继续复用；软件目录槽、激活和业务回退后端尚未实现，现有参考库仍拒绝未配置的04/55实际动作。
