# X26 上注存储与主备升级设计提案

日期：2026-11-20。状态：供用户评审，未在主板应用。用户已授权自主设计不存在现成定义的接口。这里的区域、分区名、包格式和回退策略是新设计，不宣称是厂商已经支持的功能。

## 建议结论

升级文件统一从UART8对应的RS422_RX2上注，UART6负责命令、应答和遥测。eMMC划为两套可启动系统A/B及共享业务数据区：boot1+APP1对应A，boot2+APP2对应B。平时只运行一套，接收、校验和写入另一套，试启动健康检查通过后才确认升级。SPI-NOR和SSD当前均不作为可用升级目标。

先在现有系统完成暂存、文件校验与模拟切换；用户认可布局后，再制作一次地面安装镜像和启动回退支持。首次建立A/B布局涉及重新分区，必须在地面备份和离线安装，不能在当前运行rootfs中原地执行。本提案不是授权立即格式化主板。

## 硬件与现有布局证据

主板手册明确板载128GB eMMC5.1，另有U8201 M.2 Key M 2280、PCIe2.0 x1 NVMe插槽；另两路M.2用于算力卡。手册没有声明已装SSD或给出独立SPI-NOR容量。此前实机只枚举到一块125074145280字节（116.48GiB）的eMMC，rootfs约114.12GiB，未枚举NVMe。

从已校验X26-V1.0.4-20261105的update.img前8MiB中读取厂商parameter文本，原文保存为X26-FACTORY-PARAMETER.txt。按512B扇区解释的布局如下，尺寸与此前lsblk吻合：

| 原分区名称 | 起点MiB | 大小MiB | 用途 |
|---|---:|---:|---|
| uboot | 8 | 4 | 现有引导程序 |
| misc | 12 | 4 | 厂商启动控制数据，格式未公开，不擅自复用 |
| boot | 16 | 64 | 当前唯一Linux启动镜像 |
| recovery | 80 | 128 | 厂商恢复镜像，实际恢复能力需验证 |
| backup | 208 | 32 | 厂商保留区域 |
| oem | 240 | 128 | 厂商OEM数据 |
| rootfs:grow | 368 | 至盘尾 | 当前Ubuntu及数据共用 |

这些是固件声明，不是新读取的实时GPT；新实施前需再次读取实机PARTUUID、标签、扇区大小和容量确认。eMMC硬件boot0/boot1不是上表的Linux boot分区，也不是本协议的boot1/boot2。

## 拟定的正式存储映射

前368MiB的厂商引导布局作为地面安装基线保留，区域之后重新分配。GPT本身必须更新；“保留前部”不意味着整个前368MiB逐字节不变。读取设备用分区标签和PARTUUID双重核验，不在程序中硬编码p7/p8编号。

| 新标签 | 容量 | 协议部件/区域 | 内容 |
|---|---:|---|---|
| boot_a | 256MiB | boot1=01H，eMMC1=01H | A套内核、设备树、initramfs启动镜像 |
| rootfs_a | 24GiB | APP1=03H，eMMC1=01H | A套Ubuntu、匹配内核模块及载荷程序；算法暂空 |
| boot_b | 256MiB | boot2=02H，eMMC2=02H | B套启动镜像 |
| rootfs_b | 24GiB | APP2=04H，eMMC2=02H | B套Ubuntu、模块及载荷程序 |
| sathex_data | 约67.62GiB | 不直接暴露为裸写目标 | 上注暂存、目录、业务记录和升级状态 |

具体起始字节、容量和区域映射见X26-OTA-STORAGE-PROPOSAL.json；文件apply_enabled=false，仅供校验和评审，运行代码不会据此写设备。尾部保留至少4MiB用于备份GPT和对齐；实际容量不同必须重新计算。

协议“eMMC分区1/2”在本方案中定义为逻辑系统区域A/B，不等于/dev/mmcblk0p1/p2，也不代表两颗eMMC芯片。boot1不是U-Boot/SPL，APP1不是算法APP1；前者是升级组件名，后者是遥测算法ID，分别使用不同命名空间。APP槽位包含系统文件及应用，是为了保证内核模块、依赖库与应用版本配套。

允许组合仅为(boot1,eMMC1)、(APP1,eMMC1)、(boot2,eMMC2)、(APP2,eMMC2)。交叉组合返回区域无效02H。SPI-NOR=03H默认不存在，返回02H；SSD=04H默认未安装，返回02H，将来增加SSD后另行定义，不能回落到根目录或eMMC写入。

初始由地面安装程序写入相同已验证系统到A/B，标记A为活动、B为可恢复；升级只允许写非活动槽。若A当前运行，则新包只能写boot_b/rootfs_b。原厂rootfs镜像不能直接截断到24GiB，必须离线构建或正确缩容文件系统，并确认实际文件、模块、inode及剩余空间可容纳；本次约16.1GiB已用是可行性参考，不是文件系统可直接缩容的证明。

单块eMMC上的两份拷贝可防一次升级覆盖故障，不能防整颗eMMC失效。升级状态和业务区损坏也需要独立恢复验证。

## 接收和业务数据存放

地面安装后的sathex_data挂载到/var/lib/sathex，建议预算为：inbox 8GiB、已验证包/历史包8GiB、业务记录32GiB、状态与日志2GiB、最低空闲保留16GiB，合计66GiB，小于约67.62GiB可用分区容量。此预算是逻辑上限，格式化后按statvfs实际可用空间再核对，不视为ext4已经预留足额块；接收时预留声明的文件体积和数据库/导出临时峰值。

```text
/var/lib/sathex/
  ota/inbox/<transfer-id>/     正在接收的块文件和断点位图
  ota/packages/<package-id>/  已验证的只读包与manifest
  ota/history/index.json     历史索引到不可变包ID
  ota/state/                 事务记录和启动选择日志
  records/                   星敏、固存和回放数据
  logs/                      有界日志
```

准备阶段还没有sathex_data分区，可以在现有rootfs中的/var/lib/sathex-lab做文件层验证，必须明确标为实验，不使用正式区域映射或开放分区擦写。实验目录不会因为名字叫emmc1就变成物理分区。

首包前6B给出大小和CRC-16/CCITT-FALSE；当前接收原型SQLite逐包事务可以证明小文件断点逻辑，大包正式实现改为预分配payload.part+接收位图+事务日志，避免数千万行SQLite和逐包fsync造成容量/吞吐问题。批次提交必须按先数据fsync、再位图及计数持久化的顺序，r010仅统计已持久化的包；尚未持久化的包在重启后要求重传。不能只因写缓存成功就宣布可靠接收。

暂存、验证、部署三个阶段分离：54H通过只能证明文件校验通过；04H才请求加载，且必须先完成manifest与目标兼容性检查。所有来包路径由包ID生成，包内路径需严格拒绝绝对路径、..、软链接逃逸及设备节点，不能从总线传入分区设备名。

## 包定义和大文件传输

不通过115200接口直接传17.58GiB的厂商整包。boot目标上传匹配本板的boot.img组件；APP目标上传按24GiB槽位构建的系统镜像或可验证的差分包。manifest记录board=X26、硬件版本、组件、区域、目标release、基础release、内核/模块兼容关系、压缩前后大小、每段SHA256及最终SHA256；建议包签名由地面发布私钥产生、板上只保存验证公钥。CRC检测传输错误，SHA256/签名与兼容性检查承担包级验证。

单个线上文件仍遵守u32长度，不更改3A序号/首包格式。建议单段最大128MiB，最多255段，可以表达最大31.875GiB组件包；每段是独立线上文件，每段首包有其长度和CRC，数据序号从0开始。

由于现文档缺少分段标识，提出以下新增应用约定供评审：53H的W4=1表示段文件模式，W5明确为总段数；每段文件内容前增加SATHEX段头/manifest，包含group_id、segment_index、segment_count、total_size、segment_offset、segment_length、组件/区域和hash。每段分别执行53→数据→54，只有所有段齐全并通过总hash才允许04H。中间段的54成功表示本段有效，不表示整组件已就绪；32H查询需返回group/段进度，r008对应当前transfer_id。旧发送端如果不认识该段头，只能用W4=0传≤4GiB-1的独立完整包，不能隐式回绕。

段头精确字节布局、32H响应和签名格式将在该方案被用户认可后定版；本提案不声称现有代码已支持这些扩展。整体续传按段ID+包序号定位，跨重启持久保存组标识，解决此前同参数新旧会话无法区分的问题。

## 控制指令在本布局下的动作

| 指令 | 存储动作和成功含义 |
|---|---|
| 17H | 控制上注接收门控，不切换系统，不擦盘 |
| 53H | 验证目标组合、非活动槽及容量预算；创建或恢复暂存会话；00表示准备接收 |
| 54H | 等待所有包持久化并校验CRC；验证包结构、hash和目标；CRC失败11H，其他拒绝FF |
| 55H scope=00 | 将指定非活动A/B区域标为无效并清除其boot/rootfs内容；禁止活动区域、共享数据及厂商前部区域 |
| 55H scope=01 | 只清除该区域boot_a或boot_b并标无效；与00区别明确 |
| 04H | 选定已验证包，写非活动组件、回读hash、提交待启动release，返回成功后安排重启试运行 |
| 56H | 返回当前实际运行且已确认的release；在试运行阶段应携带试运行标识，不以最新上传包名称代填 |

55是逻辑清除，不承诺物理安全擦除：底层采用经设备能力验证的discard或覆零，收到完成并确认该槽不可选为启动目标才返回00。擦除时必须先持久化禁用标志。区域已经无效且内容为空的重发可幂等成功。串口断开或超时重试不能导致擦除活动区域。

04H索引00=最近一次完整验证且目标匹配的包；01–80是持久化历史索引；F0–FF为地面预置且固定保护的恢复包。第一版仅注册F0，其他不存在索引拒绝。预算不保证128个大包同时存在，按显式索引查目录，不能用列表排序位置代替稳定索引。恢复包同样从受保护包库写入非活动槽，不能绕过目标校验直接重写当前系统。

每次切换应将boot与rootfs视为同一release组合；只有manifest明确说明现有另一组件兼容时才允许单组件更新。新内核不能搭配旧模块目录。boot.img槽位升级不包含DDR Loader、SPL、U-Boot、GPT或misc原始格式；它们只在地面维护模式下更新。

## 启动确认和失败恢复

建议地面构建时给U-Boot接入A/B选择、持久启动尝试计数、看门狗及独立恢复入口。写入槽位→回读验证→标pending(B)→重启试B；最多3次试启动，单次健康确认期限120秒；超次回A。具体超时需通过本板启动耗时测试调整。

健康确认包括：正确rootfs挂载、release及内核模块匹配、通信守护进程能够响应遥测、OTA状态可读、配置读取正常；业务需要Docker时再检查Docker READY。仅systemd进程存在或网络可Ping不算升级成功。确认后将B标good且active，保留A。升级状态采用冗余记录、单调generation及校验，写新记录持久化后才替换选择；断电不得留下两个槽都有效性未知。

这里的回退必须由启动链实现：如果新内核未启动，Linux程序无机会运行，不能靠Python脚本自己回退。U-Boot官方提供bootcount/bootlimit/altbootcmd机制作为实现参考，但尚未证明X26当前厂商U-Boot已编译启用。地面安装前应先验证启动链和看门狗；不能直接写未知位置的U-Boot环境。[U-Boot官方说明](https://docs.u-boot.org/en/v2025.07/api/bootcount.html)

原厂boot/recovery镜像虽保留在前部，但原rootfs布局已经改变，因此“保留镜像”不代表它们会自动成为可用恢复系统。必须制作并测试无需A/B rootfs即可启动的恢复initramfs或适配恢复镜像，能够选择有效槽、导出日志及接受维护指令。地面保留整盘备份和原始厂商update.img；Loader/MaskROM USB恢复只用于地面，不能作为在轨自动恢复手段。

## 链路时间与容量核算

115200/8N1时512B整帧仅线路发送就需44.44ms，理想文件速率约11227.5B/s；若每帧再等15ms则更慢，未计重传/校验/写盘。

| 文件量 | 理想下界 | 另加15ms帧间隔 |
|---|---:|---:|
| 1MiB | 约93秒 | 约125秒 |
| 64MiB | 约100分钟 | 约133分钟 |
| 17.58GiB厂商整包 | 约19.46天 | 约26.03天 |

因此在轨以小型应用包、压缩组件或有基础版本校验的差分包为主；差分需要确定的旧版本hash、非活动槽重建空间和最终全量hash。不能为了看起来更快而直接提高波特率，需两端及链路实测确认。当前协议单个4GiB-1文件不能容纳17.58GiB整包，即使物理存储放得下也不符合协议。

## 推进顺序与评审点

第一阶段在现有Ubuntu上实现UART8接收、文件暂存/CRC/hash、manifest及模拟槽位，不改GPT。第二阶段在用户批准后准备A/B地面镜像、已知恢复入口和完整备份，验证每个中断点下的恢复。第三阶段执行真实非活动槽写入、3次启动失败回退、健康确认、重复命令和断电验收，最后再合并主分支。

请优先评审四项取舍：①boot1/APP1和boot2/APP2分别组成两套系统；②24GiB rootfs×2及共享业务区；③整盘厂商固件仅地面刷，轨上组件/分段升级；④改启动链和分区必须先地面验证。此处已给出默认设计，不再要求厂商提供不存在的命名映射。
